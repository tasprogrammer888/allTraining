## 0. ภาพรวมและตำแหน่งของโมดูลในหลักสูตร

โมดูลนี้คือจุดที่ผู้เรียน **เปลี่ยนจาก "คนเขียน ladder ได้" เป็น "คนเขียนเครื่องจักรทั้งเครื่องได้"** ก่อนหน้านี้ M06 สอนให้เขียน logic ทีละก้อน, M07 ทำหน้าจอ, M08 ขยับ servo, M09 สั่ง robot, M10 ต่อสื่อสาร — แต่ยังเป็น "ชิ้นส่วนแยกกัน" โมดูล M11 คือกาวที่ประกอบทุกอย่างให้เดินเป็นเครื่องเดียวอย่างมีโครงสร้าง ปลอดภัย และซ่อมได้

> **หลักคิดประจำโมดูล:** *เครื่องจักรที่ดีไม่ใช่เครื่องที่เดินได้ แต่คือเครื่องที่ "เมื่อค้าง คนกะดึกหาเจอใน 5 นาที"* ทุกเทคนิคในโมดูลนี้ออกแบบมาเพื่อความ "ซ่อมง่าย" พอ ๆ กับ "เดินได้"

### ความต่อเนื่อง — ไม่ซ้ำ ไม่มีช่องว่าง

| สิ่งที่ "ถือว่ารู้แล้ว" (ไม่สอนซ้ำ) | สิ่งที่ "M11 สอนใหม่" | สิ่งที่ "ส่งต่อให้ M12/M13" |
|---|---|---|
| เขียน ladder, MOV, compare, timer (M06) | จัดโครงสร้างโปรแกรมทั้งเครื่อง (state machine, FB, mode) | นำ logic ต้นแบบไปรันบน hardware จริงเต็มสเกล (M12) |
| ทำหน้าจอ GOT (M07) | เชื่อม recipe/alarm กับ GOT ในเชิงระบบ | SCADA/IIoT รวมข้อมูลหลายเครื่อง (M13) |
| สั่ง servo/robot/สื่อสารทีละตัว (M08-M10) | handshake ให้ทุกตัวประสานกันไม่ชน | troubleshooting หน้างานจริง (M12) |

## บทที่ 1: สถาปัตยกรรมโปรแกรมเครื่องจักร และ State Machine (4 ชม.)

### 1.1 ทำไม "ladder ก้อนเดียว" ถึงคุมเครื่องจริงไม่ไหว

ตัวอย่าง spaghetti logic ที่เจอหน้างานบ่อย — คนเขียนพยายามคุมทั้ง cycle ใน rung ปนกัน:

```
-- เดิน cylinder, pick, place ปนใน rung เดียว ใครจะตามได้? --
| X0  X1  M5         Y10 |   <- extend
| X0  Y10 X2  T0     Y11 |   <- pick
| Y11 X3  M5  X0     Y12 |   <- place ... แก้ที่นึงพังอีกที่
```

ปัญหาที่ตามมา: output ตัวเดียวถูกสั่งหลายที่ (**double-coil**), แก้ step หนึ่งกระทบ step อื่น, ไม่มีใครรู้ว่า "ตอนนี้เครื่องอยู่ step ไหน", debug ไม่ได้

### 1.2 State Machine — แนวคิดหลัก

เครื่องจักร = **state machine**: ณ เวลาหนึ่ง อยู่ได้ **state เดียว**, มี **action** ประจำ state, และเลื่อนไป state ถัดไปเมื่อ **transition condition** เป็นจริง

| องค์ประกอบ | ความหมาย | ตัวอย่าง (ลิฟต์) |
|---|---|---|
| State / Step | สถานะปัจจุบัน | "กำลังขึ้นชั้น 3" |
| Action | สิ่งที่ทำใน state นั้น | สั่งมอเตอร์ขึ้น |
| Transition | เงื่อนไขเลื่อน state | ถึง limit switch ชั้น 3 |

Analogy ที่ผู้เรียนเห็นภาพ: **เครื่องซักผ้า** (แช่ → ซัก → ปั่น → สะบัด) แต่ละโหมดมีเงื่อนไขจบชัดเจนก่อนไปขั้นต่อไป

### 1.3 สถาปัตยกรรมโปรแกรมมาตรฐาน 5 ชั้น (สำคัญที่สุดในบทนี้)

```
┌─────────────────────────────────────────────┐
│ ชั้น 1: SAFETY / INTERLOCK                    │  <- scan ก่อนเสมอ, ตัด motion ได้ทันที
├─────────────────────────────────────────────┤
│ ชั้น 2: MODE MANAGER (Auto/Manual/Step/Home) │
├─────────────────────────────────────────────┤
│ ชั้น 3: SEQUENCE (step/SFC) -> สั่งผ่าน M     │  <- ไม่สั่ง Y ตรง!
├─────────────────────────────────────────────┤
│ ชั้น 4: OUTPUT MAPPING (M -> Y จุดเดียว)     │  <- decoupling กัน double-coil
├─────────────────────────────────────────────┤
│ ชั้น 5: ALARM & DIAGNOSTICS                   │
└─────────────────────────────────────────────┘
```

**หลัก Decoupling (หัวใจของความซ่อมง่าย):** sequence ไม่สั่ง `Y10` ตรง ๆ แต่สั่ง internal bit `M_Cyl1_Ext` แล้วชั้น Output Mapping รวมเงื่อนไข auto/manual ที่ **จุดเดียว**:

```
-- ชั้น 4: Output Mapping (Y10 ถูกเขียนที่เดียวในทั้งโปรแกรม) --
|  M_Cyl1_Ext_Auto                       Y10  |
|  M_Cyl1_Ext_Man --|                         |
```
ผลคือ auto กับ manual ใช้ output ร่วมกันได้โดยไม่ชน และไล่หา "ใครสั่ง Y10" ได้ที่เดียว

### 1.4 Workflow: Design-before-Code
**อ่านโจทย์กระบวนการ → ทำ I-O list → ร่าง sequence chart → ค่อยเขียนโค้ด** (ห้ามเขียนโค้ดก่อนออกแบบ — เป็นกฎเหล็กของโมดูล และเป็นเหตุผลที่ Lab 1 ต้องผ่านก่อน Lab 2)

## บทที่ 2: Step Sequence บน GX Works3 — Step Register & SFC (6 ชม.)

### 2.1 วิธีที่ 1: Step Number ด้วย Data Register

แนวคิด: เก็บ "หมายเลข step ปัจจุบัน" ใน `D100` แล้วใช้ compare เปิด action

```
-- เปิด action ของ step 10 --
|  = K10 D100      ...action ของ step 10... |

-- Transition: step 10 -> 20 (ต้องใช้ rising edge กัน step กระโดด!) --
|  = K10 D100   X_Done                       |
|                 |--[PLS M_T10]              |   <- one-shot
|  M_T10          [MOV K20 D100]              |   <- เลื่อน step
```

> **กับดักจริง #1:** ถ้าไม่ใช้ one-shot และ transition ของ step 20 บังเอิญจริงด้วย ค่า D100 จะวิ่ง 10→20→30 ใน scan เดียว = เครื่องกระโดดข้าม step → ใช้ `PLS`/`LDP` ทุก transition

> **กับดักจริง #2:** วาง MOV เลื่อน step ผิดลำดับ scan อาจทำให้ compare ของ step ใหม่จริงทันทีใน scan เดียวกัน → ออกแบบให้เลื่อน step ที่ "ปลาย" ของ block

### 2.2 วิธีที่ 2: SFC (Sequential Function Chart)

GX Works3 รองรับ SFC เต็มรูปแบบ (ยืนยันจาก FX5U manual) — เขียนเป็น **step block + transition** มองเห็นลำดับเป็นภาพ:

```
   [S0] Initial (Home)
    |--- (T0: Start pressed & Ready)
   [S10] Feed
    |--- (T1: Part detected) ──┐selective branch
    |--- (T1b: No part) ───────┘──> [S90] Reject
   [S20] Pick      ══╗ parallel branch (สั่งพร้อมกัน)
   [S21] Lift      ══╝
    |--- (join: ทั้งคู่ done)
   [S30] Place ...
```

- **Selective branch:** แยกทางตามเงื่อนไข (เจอ/ไม่เจอชิ้นงาน)
- **Parallel branch:** สั่งหลายอย่างพร้อมกันแล้ว **join** รอทุกเส้น done

### 2.3 Step Reset / Home / Resume

ทุก sequence ต้องมีทางกลับ: ปุ่ม Home → `MOV K0 D100` + สั่งทุกแกนกลับ origin **อย่างปลอดภัย** (ไม่กระชาก, ตรวจ position ก่อน)

### 2.4 เกณฑ์เลือก Step Register vs SFC

| | Step Register | SFC |
|---|---|---|
| มองเห็นลำดับ | ต้องไล่อ่าน | เห็นเป็นภาพ |
| branch ซับซ้อน | จัดการเองยาก | มี built-in |
| ทีม service ทั่วไปอ่าน | คุ้นกว่า (เป็น ladder) | ต้องเรียน SFC |
| **เหมาะกับ** | step ตรงไปตรงมา, ทีมถนัด ladder | เครื่องซับซ้อน หลาย branch |

## บทที่ 3: Structured & Modular Programming — FB / FUN (5 ชม.)

### 3.1 FB vs FUN vs Subroutine

| | มี memory (instance)? | ใช้เมื่อ |
|---|---|---|
| **FB** (Function Block) | มี (เก็บ state, timer ภายใน) | อุปกรณ์ที่มีสถานะ: cylinder, motor, axis |
| **FUN** (Function) | ไม่มี (in→out ทันที) | คำนวณล้วน: scaling, แปลงหน่วย |
| **Subroutine (CALL/P)** | ใช้ device global | code เก่า / งานง่าย |

### 3.2 ตัวอย่าง FB_Cylinder (โครงโค้ดจริง)

**Label ของ FB:**
| ชื่อ | Class | Type | หน้าที่ |
|---|---|---|---|
| `i_Extend` | VAR_INPUT | Bit | สั่งดันออก |
| `i_Retract` | VAR_INPUT | Bit | สั่งดึงกลับ |
| `i_SnsExt` | VAR_INPUT | Bit | sensor ดันสุด |
| `i_SnsRet` | VAR_INPUT | Bit | sensor ดึงสุด |
| `i_Timeout` | VAR_INPUT | Time | เวล่า timeout |
| `o_Extended` | VAR_OUTPUT | Bit | ดันสุดแล้ว |
| `o_Fault` | VAR_OUTPUT | Bit | fault (ไม่ถึงใน timeout) |
| `t_Mon` | VAR (internal) | Timer | จับเวลาภายใน |

```
-- logic ภายใน FB_Cylinder --
|  i_Extend  i_SnsExt(/)                  Y_Sol  |   <- สั่ง solenoid
|  i_Extend  i_SnsExt(/)        [TON t_Mon i_Timeout]|
|  t_Mon                                  o_Fault |   <- timeout = fault
|  i_SnsExt                               o_Extended|
```

**นำไปใช้ (instance หลายตัว — เขียนครั้งเดียว):**
```
FB_Cylinder Cyl1( i_Extend:=M_Cyl1_Ext, i_SnsExt:=X10, ... );
FB_Cylinder Cyl2( i_Extend:=M_Cyl2_Ext, i_SnsExt:=X12, ... );
FB_Cylinder Cyl3( ... );   <- ทุกตัวมี timer/state ของตัวเอง
```

> **กับดักจริง:** ห้ามใช้ instance เดียวกันคุมหลาย cylinder — state/timer จะชนกัน ต้องสร้าง instance แยกทุกตัว

### 3.3 FB_ServoAxis (ห่อ MELSERVO ให้สั่งง่าย)
ห่อ positioning ของ MR-J4/J5: `i_Target, i_Speed, i_Start` → `o_Busy, o_InPos, o_Alarm` เพื่อให้ sequence สั่งแค่ "ไปตำแหน่ง X" โดยไม่ต้องยุ่งกับ signal ดิบทุกครั้ง

### 3.4 Label และการตั้งชื่อ
ใช้ชื่อสื่อความหมาย (`M_Cyl1_Ext` ไม่ใช่ `M523`) — ทีมกะดึกที่มาซ่อมตอนตี 3 จะขอบคุณ

## บทที่ 4: Data Handling, Index Addressing และ Recipe (4 ชม.)

### 4.1 Memory Map ที่มีเอกสารกำกับ
จัด D/R register เป็นโซน: working, recipe, alarm, comm — และ **เขียนเอกสาร map ทุกครั้ง** (เป็นส่วนหนึ่งของ deliverable)

### 4.2 Indirect Addressing ด้วย Index Z (Z0–Z23 บน FX5U)

วน loop อ่านตำแหน่งงานหลายจุดจาก data table:
```
-- อ่าน D200+Z (ตำแหน่งที่ Z) --
|             [MOV D200Z  D_Work]            |
|             [INC Z]                        |
-- GUARD กัน index เกิน! --
|  > Z K9     [MOV K0 Z]                     |   <- กันอ่านนอกพื้นที่
```
> **กับดักจริง:** ลืม guard Z → อ่าน/เขียน device นอกขอบเขต ค่าเพี้ยนแบบหาสาเหตุยากมาก

### 4.3 Recipe — เปลี่ยนงานจากหน้าจอ

แนวคิด: 1 สูตร = 1 ชุด parameter

| Recipe | Pick Pos | Place Pos | Speed | Count |
|---|---|---|---|---|
| 1 (ชิ้นเล็ก) | 1000 | 5000 | 800 | 50 |
| 2 (ชิ้นใหญ่) | 1200 | 5200 | 400 | 20 |

Flow: GOT เลือกสูตร → กด **Load** → copy เข้า working register → **validate min/max** → sequence ใช้

```
-- VALIDATE ก่อนใช้ (กันป้อนตำแหน่งเกิน stroke ทำเครื่องชน!) --
|  > D_PickPos K8000      [SET M_Recipe_Err] |
|  M_Recipe_Err(/)        [MOV D_PickPos D_WorkPos]|
```
> **กับดักจริงที่ทำเครื่องพังมาแล้ว:** recipe จาก HMI ไม่ validate → operator พิมพ์ 80000 แทน 8000 → แกนวิ่งชน end stop. **ต้อง clamp/reject เสมอ**

### 4.4 Scaling และ Electronic Gear
แปลงหน่วยตำแหน่ง/ความเร็วให้ตรงกับ servo (pulse/unit, electronic gear ของ MR-J) และ scaling ค่า analog (`SCL`) ให้เป็นหน่วยวิศวกรรม

## บทที่ 5: Error Handling และ Alarm Management (4 ชม.)

### 5.1 ระดับของ Fault

| ระดับ | พฤติกรรมเครื่อง | ตัวอย่าง |
|---|---|---|
| **Warning** | เดินต่อ + เตือน | นับใกล้ครบ, air ต่ำเล็กน้อย |
| **Critical/Fault** | หยุดจบ cycle อย่างปลอดภัย | cylinder timeout, sensor หาย |
| **E-Stop** | ตัด motion ทันที (hardware) | กด E-Stop, door เปิด |

### 5.2 Timeout ทุก Motion (กฎเหล็ก)
**ทุก motion ต้องมี timer คุม** — cylinder ไม่ถึง sensor ใน X วิ / servo ไม่ INP ใน Y วิ = latch alarm. นี่คือ safety net ที่ทำให้ step ไม่ค้างเงียบ ๆ

```
|  M_Cyl1_Ext  X_SnsExt(/)   [TON T1 K30]   |   <- 3.0 วิ
|  T1                        [SET M_ALM_Cyl1]|   <- latch
```

### 5.3 First-Fault Detection (สำคัญตอนหา root cause)
เมื่อ fault หลายตัวเด้งพร้อมกัน ต้องรู้ว่า **ตัวไหนเกิดก่อน**:
```
|  M_AnyAlarm(/)  M_ALM_Cyl1   [SET M_FF_Cyl1]|  <- latch เฉพาะตอนยังไม่มี alarm อื่น
|  M_AnyAlarm(/)  M_ALM_Servo  [SET M_FF_Servo]|
```

### 5.4 Alarm Code + GOT
ตั้ง numbering convention (เช่น 1xx=cylinder, 2xx=servo, 3xx=robot) map ขึ้น **GOT User Alarm + Alarm History** เพื่อเก็บประวัติ + timestamp

**อ่าน alarm จาก manual จริง:** เชื่อม alarm code ของ MELSERVO (เช่น `AL.xx`) มาแสดงพร้อมคำแนะนำวิธีแก้บนหน้าจอ — ฝึกใน Lab 6/7

### 5.5 Reset ที่ปลอดภัย
เคลียร์ alarm ได้ **เฉพาะเมื่อ** condition กลับปกติ **และ** กดปุ่ม reset (ห้าม auto-clear ขณะยังอันตราย):
```
|  X_ResetBtn  M_CondNormal   [RST M_ALM_Cyl1]|
```

## บทที่ 6: Machine Mode, Handshaking และ Safety/Interlock (5 ชม.)

### 6.1 Mode Manager
4 mode: **Auto / Manual(Jog) / Step / Home** — สลับได้ **เฉพาะตอนเครื่อง idle** (ห้ามสลับกลาง cycle):
```
|  M_Idle  X_SelAuto   [SET M_ModeAuto] [RST M_ModeMan]|
```

### 6.2 Handshaking — 4-Way Pattern (กันชน/กัน drop คำสั่ง)

```
PLC: Request ──────►
              ◄────── Busy        (อุปกรณ์รับงาน)
              ◄────── Done/Error  (ทำเสร็จ/ผิดพลาด)
PLC: Reset Request ──►            (เคลียร์ พร้อมรอบใหม่)
+ ทุกขั้นมี TIMEOUT (ถ้าไม่ Busy ใน X วิ = handshake fault)
```

### 6.3 Handshake PLC ↔ MELSERVO
อ่าน signal จาก MR-J4/J5 manual:
| Signal | ทิศทาง | ความหมาย |
|---|---|---|
| Positioning Start | PLC→Servo | เริ่มวิ่ง |
| INP (In-Position) | Servo→PLC | ถึงตำแหน่ง |
| RD (Ready) | Servo→PLC | พร้อม |
| ALM (Alarm) | Servo→PLC | ผิดพลาด |

ลำดับถูกต้อง: รอ `RD` → set target → `Start` → รอ `Busy` หาย + `INP` → done

### 6.4 Handshake PLC ↔ KUKA Robot
ผ่าน digital I-O / Ethernet (อ่านจาก KUKA I-O interface doc):
```
PLC -> Robot:  ProgramNo (BCD/binary) + Start strobe
Robot -> PLC:  RobBusy, RobDone, RobFault
```
```
-- ตัวอย่าง: trigger robot ทำ pick (program 5) --
|  M_Step_Pick   [MOV K5 K2Y20]              |   <- ส่ง program no.
|  M_Step_Pick   X_RobReady   [SET Y30]      |   <- start strobe
|  X_RobBusy                  [RST Y30]      |   <- ปล่อย strobe เมื่อ robot รับ
|  X_RobDone                  [SET M_PickDone]|
```
ฝั่ง KRL (เพื่อให้ผู้เรียนเห็นภาพสองฝั่ง):
```krl
; KUKA side - รอ start จาก PLC แล้วทำงานตาม program number
WAIT FOR $IN[10]            ; start strobe จาก PLC
$OUT[20] = TRUE             ; RobBusy
PTP P_Pick                  ; เคลื่อนไป pick
$OUT[20] = FALSE            ; clear busy
$OUT[21] = TRUE             ; RobDone
```

### 6.5 Interlock — กันชนของจริง
```
-- กัน robot เข้า zone ตอน cylinder ยังไม่ retract --
|  M_Req_RobEnter  X_Cyl1_Ret   [SET M_RobEnter_OK]|
|  X_Cyl1_Ret(/)               [RST M_RobEnter_OK]|  <- cylinder โผล่ = ห้ามเข้า
```

### 6.6 Safety: Hardwired ≠ PLC Logic (สำคัญมาก)

> **กฎความปลอดภัยข้อสำคัญที่สุด:** E-Stop และ safety door **ต้องตัด motion ด้วย hardware/safety relay** (category 0/1) — **ห้ามพึ่ง PLC logic อย่างเดียว** PLC ใช้สำหรับ functional interlock เท่านั้น (กันชน, ลำดับงาน) ไม่ใช่ safety function

**E-Stop Recovery (ห้าม auto-restart):**
1. E-Stop/door → safety relay ตัด power motion ทันที (hardware)
2. PLC ตรวจพบ → latch state, หยุด sequence
3. แก้สาเหตุ → ปลด E-Stop → **กด Reset** (manual)
4. **Re-home / confirm position** ก่อนเดินต่อ (เพราะตำแหน่งอาจเลื่อนตอนตัดไฟ)
5. ห้ามเครื่องกระโดดเดินต่อเองโดยอัตโนมัติ

## ข้อผิดพลาดที่พบบ่อย + Safety Checklist

### Top mistakes (จากหน้างานจริง)
- [ ] **Double-coil** → ใช้ decoupling, สั่ง M แล้ว map Y จุดเดียว
- [ ] **Step ค้าง** (transition ไม่มีทางจริง) → ทุก motion มี timeout เป็น safety net
- [ ] **Step กระโดด** (ไม่ใช้ edge) → PLS/LDP ทุก transition
- [ ] **Instance FB ซ้ำ** → สร้าง instance แยกทุกอุปกรณ์
- [ ] **สั่ง servo/robot ไม่รอ feedback** → 4-way handshake + timeout
- [ ] **Recipe ไม่ validate** → clamp/reject min-max ก่อนใช้
- [ ] **Index Z ไม่ guard** → ตรวจขอบเขตก่อนใช้
- [ ] **สับสน safety vs PLC interlock** → E-Stop/door = hardwired/safety relay
- [ ] **Auto-restart หลัง E-Stop** → บังคับ reset + re-home
- [ ] **ไม่มี first-fault** → latch ตัวแรกที่เกิด
- [ ] **เดิน Auto เต็มความเร็วเลย** → ไล่ commissioning ทีละชั้น
- [ ] **ลืม backup** → version backup ก่อนแก้เสมอ

### Safety gate (ต้องผ่านจึงผ่านโมดูล)
- [ ] Lab 0: pre-power checklist + ทดสอบ E-Stop/door ตัด motion จริง
- [ ] Lab 8: E-Stop recovery ถูกขั้นตอน, ไม่ auto-restart
